# Runtime fixes — 2026-09-21

## Root cause of the silent `/start` failure
The runtime image did not compile PHP `mbstring`, while `BotFlow` calls `mb_substr()` on every new Telegram participant. The processing worker therefore failed as soon as it tried to process `/start`. The polling process itself also only logged to Laravel's daily file, making the failure look like a silent polling problem.

## Fixes applied
- Added PHP `mbstring` plus XML/DOM extensions to the Docker runtime.
- Docker services now log Laravel output to stderr, so `docker compose logs -f ...` works.
- Added HOME/XDG writable paths so PsySH/Tinker no longer fails on `/var/www/.config`.
- Poller now prints startup, received-update, lock, retry, and shutdown status to the container console.
- Poller checks/removes an active Telegram webhook without dropping pending updates, enforcing polling mode.
- Poll cursor initialization is explicit and null-safe.
- Queue/reply jobs no longer silently disappear on lock/order contention; they release for retry.
- Increased processing/reply worker tries from 1 to 10.
- Added `php artisan telegram:doctor` for end-to-end operational diagnostics.
- Added participant `last_name` migration and refresh Telegram profile metadata on interaction.
- Local `.env` uses `APP_URL=http://localhost:8080` and non-secure session cookies for local HTTP. Use secure cookies again behind HTTPS in production.

## After replacing the project
Rebuild because PHP extensions changed:

```bash
docker compose down
docker compose build --no-cache
docker compose up -d postgres redis app nginx
docker compose exec app php artisan migrate --force
docker compose up -d
```

Do **not** use `docker compose down -v`.

Then:

```bash
docker compose exec app php artisan telegram:doctor
docker compose logs -f telegram-polling queue queue-replies
```

Send `/start`. The logs should show the polling process receiving an update and the processing/reply workers handling it.
